# Hub contract for the watchdog / installer (Phase 1)

Implemented by `hub/app.py` (+ `forge_store.py`, `forge_cluster.py`, `forge_bundle.py`). All JSON.
Tokens live in `data/config.json`: `ui_token`, `agent_token`, `cluster_token` (+ optional `node_id`, `seed_peers`).
`cluster_token` is auto-generated by a hub if missing; copy the whole config between nodes (`/cluster/bootstrap`).

## Environment
| var | default | meaning |
|---|---|---|
| `FORGE_DATA` | `<repo>/data` | config.json, forge.db |
| `FORGE_RELEASE_DIR` | repo root (parent of `hub/`) | the RUNNING release (must contain `hub/ agent/ watchdog/ requirements.txt VERSION`); this is what gets zipped for `/cluster/bundle` when no newer release is stored |
| `FORGE_RELEASES_DIR` | `<FORGE_DATA>/../releases` | where `/cluster/publish` stores new releases. In the installed layout set it to `%ProgramData%\Forge\releases` |

`node_id` = config `node_id`, else lowercased `COMPUTERNAME`.

## Auth headers
- Cluster endpoints: `X-Cluster-Token: <cluster_token>`.
- `GET /cluster/bundle` also accepts the agent token (`X-Agent-Token` header or `?t=`) so a fresh installer can fetch it.
- `GET /cluster/bootstrap?t=<agent_token>`.
- `/healthz` needs no auth: `{ok, node_id, role}`.

## Status: `GET /cluster/status`
```json
{"node_id":"forge-01","role":"leader|standby|starting","leader_id":"forge-01|null","eligible":true,
 "version":"1.1.0","running_version":"1.0.0","bundle_sha256":"<hex>","sync_cursor":1.7e9,"now":1.7e9}
```
**`version` and `bundle_sha256` describe the LATEST AVAILABLE bundle on this hub** = max(running release,
any release stored by `/cluster/publish`). `running_version` is what the process is actually running.
(Deviation from spec wording: this lets "publish to hub X" propagate through the spec's rule
"upgrade to the highest `version` seen among healthy peers".) The local watchdog should therefore also
query `http://localhost:8787/cluster/status`: if its `version` > the `current` release, install it.

## Bundle download: `GET /cluster/bundle[?version=X.Y.Z]`
Returns `application/zip`; headers `X-Bundle-Version`, `X-Bundle-SHA256`. No `version` = latest available
(the one in status, so `sha256(body) == status.bundle_sha256`). 404 for unknown versions.
Zip layout: `hub/ agent/ watchdog/ requirements.txt VERSION` at the zip root. The zip of the running release is
deterministic (sorted entries, fixed timestamps, no `__pycache__`/`*.pyc`), so identical releases have identical sha on every node.

## Publish: `POST /cluster/publish` (cluster token, body = raw zip bytes, `Content-Type: application/zip`)
Validates: valid zip; no absolute/`..` paths; `VERSION` and `hub/app.py` present; VERSION matches `^\d+\.\d+\.\d+$`
and is strictly greater than the latest available version; `hub/app.py` compiles. Size <= 200 MB.
Success `200 {"ok":true,"version":"1.1.0","sha256":"<hex>"}`. Errors: `400` (invalid), `409` (not newer), `413` (too big), `401`.
Side effects: stored at `<FORGE_RELEASES_DIR>\<ver>\` containing `bundle.zip`, `bundle.sha256` and the **already
extracted** bundle files (`hub\`, `agent\`, ...). The hub does NOT flip junctions, install requirements or restart anything:
the watchdog does (either via the local `releases\<ver>` directory or by downloading from `localhost`). Publishing to a standby
is fine; it is not forwarded to the leader.

## Cluster join / bootstrap
- `GET /cluster/bootstrap?t=<agent_token>` -> `{ui_token, agent_token, cluster_token, peers:[{id,priority,urls}], bundle_version, bundle_sha256}`.
- `POST /cluster/join` `{id, urls:[...]}` (cluster token) -> `{id, priority, urls}`. Upserts the peer (priority = existing or max+1).
  Answered by the leader; a standby proxies it to the leader (503 `no leader` if none).
- **Seeding a new node:** a fresh hub only knows itself and would elect itself leader. The installer MUST put the peer list
  into the new node's `config.json` as `"seed_peers": [{"id","priority","urls":[...]}, ...]` (take it from
  `/cluster/bootstrap` -> `peers`, then add this node via `/cluster/join` on the leader). Seeds are inserted with a tiny
  `updated`, so replicated rows from the leader always override them.

## Cluster internals (for reference)
`GET /cluster/sync?since=<float>` -> `{now, tables:{peers,nodes,jobs,events,settings}, deleted:[{table,id,updated}], more, next_since?}`.
`deleted` (tombstones) is an addition to the spec so node/peer removals replicate.
Standbys answer `/cluster/*`, `/healthz`, `/`, `/static/*`, `/agent/*`, `/api/login|logout|enroll` locally and proxy all other requests
to the leader with `X-Forwarded-For` + `X-Forge-Via: <node_id>`; no leader -> `503 {"detail":"no leader","role","peers":[ids]}`.

## Agent-facing (unchanged for v1 agents)
- `POST /api/agent/report` (`X-Agent-Token`) response adds `settings:{work_root,max_jobs}`, `hub_urls:[...]` (all peer urls, priority order),
  `bundle_version` (latest available). Job `id`s are now strings. `metrics.work_root`, `metrics.work_root_free_gb`,
  `metrics.watchdog` and `bundle_version` (top-level body field or `metrics.bundle_version`) are stored as sent.
- `agent_version` in the response is read from `agent/legacy/forge-agent-v1.ps1` (1.1.1). `GET /agent/forge-agent.ps1` serves that same
  v1 file, so v1 agents never jump to v2. v2 agent: `GET /agent/v2/forge-agent.ps1`. Installer: `GET /agent/install.ps1?t=<agent_token>`
  (`__HUB__`, `__TOKEN__` substituted).
- `metrics.watchdog` should be the contents of `watchdog.json`: `{last_run: <epoch secs or ISO-8601>, actions: [...]}`;
  the hub raises a `watchdog_stale` alert when `last_run` is older than 300 s.

## UI endpoints added
`GET /api/health` -> `{now, alerts:[{level,kind,node_id,msg}], nodes:[{id,online,bundle_version,behind,watchdog_last_run,watchdog_last_action}],
cluster, leader_id, running_version, bundle_version}`; alert kinds: `node_offline, disk_full (>=90%), version_behind, watchdog_stale, hub_down`.
`GET /api/state` adds `cluster:{leader_id,viewing,peers:[{id,priority,urls,role,version,healthy,last_ok,lag_s}]}` and per-node `settings`, `bundle_version`.
`PATCH /api/peers/{id}` `{priority}`, `DELETE /api/peers/{id}`, `PUT /api/nodes/{id}/settings` `{work_root?, max_jobs?}` (`""`/null clears work_root; max_jobs 1-64).
`POST /api/jobs` accepts `node_id:"auto"`; response `{id, node_id}` (node_id is `"auto"` until resolved). Job rows carry `requested`.

## 2.1: SYSTEM admin lane
- Jobs carry `run_as` (`user` default | `system`). Engines `action` (allowlisted, `action` + `args`) and `admin` (free-form
  PowerShell) always run as `system`; `claude|codex|shell` are user-lane only (400 if `run_as:"system"`). System jobs need a
  concrete `node_id` (no `auto`). Catalog = `hub/actions.json` (name, description, `destructive`, arg schema), served by
  `GET /api/actions` (+ `admin_lane_enabled`). `POST /api/jobs` validates action name/args (400) and requires `"confirm": true`
  for engine `admin` and destructive actions (400 `confirmation required`). Every system job emits a `warn` event
  `ADMIN ...` / `ACTION <name> ...` with `(source <source>)`. Hub config `admin_lane_enabled: false` -> job created as `failed`.
- `POST /api/agent/report` with `lane:"system"`: minimal body `{node_id, lane, capacity, running, boot, agent_version}`;
  recorded in `nodes.sys_last_seen/sys_capacity/sys_version` only (user metrics untouched). Dispatch is lane-filtered:
  reports without `lane` (v1 / 2.0.x agents) are the user lane and never receive system jobs (rows with `run_as` NULL count as user).
  Lost-job detection and `boot` failure are per lane.
- `/api/state`, `/api/health`, `/api/nodes/{id}` nodes gain `system_lane: {online, last_seen, capacity, version}`; job rows carry
  `run_as`, `action`, `args`. New columns are added to existing databases with `ALTER TABLE`.

# Phase 2 (hub 2.2.0): rollout lease, sessions, projects, briefs, scheduler

Implements SPEC-phase2.md sections A-G (+ the API needs of I). New code: `forge_lease.py`, `forge_sched.py`,
`forge_projects.py`, `forge_phase2.py` (wired in `app.py`). All errors are `{"detail": "..."}`.
New persistent tables replicate to standbys exactly like Phase 1 tables (`updated` column, TEXT ids, tombstones):
`projects, project_alias, sessions, repos, briefs, cooldowns, bad_versions, leases`. **Not replicated (ephemeral, leader memory):**
watchers and transcripts. Standbys proxy every non-`/cluster/*` call to the leader, so agents/UI may talk to any hub.
New `jobs` columns (ALTER TABLE): `resume, project_id, attempts, wait_reason, model, req_engine`.

## A. Update lease / fleet-bad (cluster token; standbys proxy these to the leader, 503 `no leader` if none)
- `POST /cluster/update-lease` `{node_id, version}` -> `200 {granted, holder, retry_after_s}` plus optional `reason`
  (`"lease held" | "waiting for earlier node" | "fleet-bad" | "unknown peer"`) and `waiting_for` (peer id).
  `node_id` is the peer id (same as the hub's node id). `version` must match `^\d+\.\d+\.\d+$` (422 otherwise).
  Granted -> `holder == node_id`, `retry_after_s: 0`; calling again while holding renews the 10 min TTL.
  Denied -> `retry_after_s` is the suggested poll delay (5-30; 300 for fleet-bad).
- **Canary (2.2.1)**: `PUT /api/nodes/{id}/settings {"canary": true|false}` (bool, 400 otherwise; stored in the replicated `settings` table, returned
  by the PUT and in `/api/state` node `settings`, NOT sent to agents). Flagged non-leader peers go first; with no flag set the order below is unchanged.
- **Order**: non-leader peers by DESCENDING priority number (canary = lowest priority), the current leader LAST. A node is
  granted only if every earlier node already runs `running_version >= version`, or has been unreachable (leader's view) for
  >= 10 min (skipped). One holder at a time; TTL 600 s; the lease row is replicated, so a new leader inherits it.
- **Auto release**: when, for 60 s straight (leader-observed), the holder's hub is healthy, reports `running_version >= version` AND `eligible:true`
  in `/cluster/status`, AND that machine's agent is online and reports `bundle_version >= version` (2.2.1; hub healthy alone is not enough).
  Explicit: `DELETE /cluster/update-lease/{node_id}` -> `{ok, released}` (`released:false` if that node was not the holder).
- `GET /cluster/update-lease` -> `{lease: {holder, version, expires_in_s} | null, bad_versions: [...]}` (local, any hub).
- **Fleet-bad**: if the holder reached `version` (healthy, running_version >= version) and later reports a LOWER running_version
  (rollback), the leader records the version in `bad_versions`, releases the lease and raises a UI alert `fleet_bad_version`.
  Optional explicit report from a watchdog that rolled back: `POST /cluster/bad-version {version, node_id?, reason?}` ->
  `{ok, bad_versions}`. Admin clear: `DELETE /cluster/bad-version/{version}` -> `{ok, cleared, bad_versions}`.
  A lease request for a fleet-bad version is denied with `reason: "fleet-bad"`.
- `GET /cluster/status` gains `bad_versions: ["2.3.0"]` and `update_lease: {holder, version, expires_in_s} | null`.
  `GET /api/health` gains `bad_versions`, `update_lease`, `cooldowns` (+ alert kind `fleet_bad_version`).
- Watchdog contract: before activating a newer version, `POST /cluster/update-lease` against any hub (via `hub_urls`); if no
  leader answers (connection error / 503) for > 5 min it may proceed (lone survivor); never install a version listed in
  `bad_versions`; `DELETE` the lease after a failed activation/rollback (and ideally also `POST /cluster/bad-version`).

## B/E. Session index and projects
- `POST /api/agent/sessions` (agent token) `{node_id, sessions:[{tool,session_id,cwd,git_remote,git_branch,title,started,
  last_activity,messages,tokens,state,remote_control,pid,model}], removed:[...], t3?: "unsupported"}` -> `{ok, accepted, changed}`.
  Upsert by `(tool, session_id)`; tools `claude|codex|t3` (others ignored); sessions idle > 14 days ignored; `started` and
  `last_activity` may be epoch seconds (ms tolerated) or ISO-8601; `title` is re-redacted (see **Redaction** below) and cut to 140;
  `git_remote` is normalized by the hub (`github.com/owner/repo`); rows are only written when a field other than `last_activity`
  changed or `last_activity` moved by more than 60 s (2.2.1: keeps replication churn down). `removed`: bare session ids (or `tool:id`) deleted for that node. Sessions may be posted in batches (any subset).
  `state` is stored as sent; the hub downgrades `live` on read when the node is offline (decays by `last_activity` age).
- `POST /api/agent/commits` (agent token) `{node_id, repos:[{cwd,git_remote,branch,dirty,ahead,behind,commits:[{sha,author,ts,subject}]}]}` -> `{ok, changed}`.
- Project key: normalized remote; `misc:<node>` for user-profile root / `Windows\system32` / any `temp` dir / `\forge\scratch`
  (named "Scratch / misc"); else `local:<node>:<cwd-lower>`. Projects auto-create on first sighting (sessions, commits, jobs with a cwd).
- A job's project: its `project_id` when that names an existing project (UI "New task here" / Continue send it); otherwise by
  `(node, cwd)` via the `repos` table, then the `sessions` table (same node + folder), else `local:<node>:<cwd>`. A job with a valid
  `project_id` never auto-creates a project.
- `GET /api/projects`, `GET /api/projects/{id}`, `PATCH /api/projects/{id}`, `POST /api/projects/merge {ids}` as in the spec. List rows
  carry `ahead` / `behind` (max over the project's working copies) next to `dirty_any`. Detail adds
  `sessions` (all tools; forge jobs appear as `tool:"forge"`, `session_id` = job id, with `status`), `commits`, `repos`, `briefs`.
  Merge keeps `project_alias` rows so future sessions of merged keys map to the surviving project (first id).
- Session row fields in `sessions[]`: `tool, session_id, node_id, cwd, git_remote, git_branch, title, started, last_activity, messages,
  tokens, state, remote_control, pid, model, project_key`.

## C. Live transcript (ephemeral)
- `POST /api/sessions/{tool}/{id}/watch` (UI) -> `{ok, node_id, ttl_s: 30}` (404 unknown session). UI refreshes every 10 s.
- Report response (user lane) gains `watch: [{tool, session_id, since}]` for that node, only while a watcher is alive (30 s TTL).
  `since` is the **agent's own `cursor`** echoed back from its last `POST /api/agent/transcript` for that session, or `null` when the
  hub has nothing (first call: send the last 200 events).
- `POST /api/agent/transcript` (agent token) `{node_id, tool, session_id, cursor, events:[{ts,role,kind,text,tool_name?,collapsed}], done}` ->
  `{ok, accepted}`. Hub redacts again, caps text at 4000 chars, keeps the last 1000 events per session, unknown roles -> `system`.
- `GET /api/sessions/{tool}/{id}/transcript?since=<seq>` -> `{events:[{seq,...}], cursor: <last seq>, done, available}`.
  `tool=forge` is synthesized from the job (prompt = user event, output = assistant events). Unwatched transcripts are dropped after 10 min.

## D. Continue / take over
`POST /api/jobs` accepts `resume: {tool: "claude"|"codex", session_id}` (+ `force: true`, `engine` optional, `node_id` may be the session's node or `auto`,
`cwd` is forced to the session's cwd, engine derived from `resume.tool`). 404 unknown session, 400 wrong node/tool, **409 `session is live in a terminal`**
when the session's effective state is `live` and it has a `pid`, unless `force`. The dispatched job item carries `resume: {tool, session_id}`.

## F. Briefs / ollama
- Job `engine: "ollama"` (+ `model`); dispatch items carry `model` (default hub config `brief_model`, `qwen2.5:14b`) and, for brief jobs, `source: "brief"`.
  Claude brief jobs carry `model: "haiku"` (agent should pass `--model haiku`). The agent returns the model's answer as the job output; progress lines starting with
  `pulling `, `verifying `, `writing manifest`, `success` or `[ollama]` are stripped before the text is stored in `briefs`.
- **2.2.1 schedule**: the automatic loop runs only inside config `brief_window` (local time, default `"00:00-07:00"`; `"HH:MM-HH:MM"`,
  wraps midnight, `"always"` = all day) and only while the brief node's GPU util (`metrics.gpu[].util`, max) is below `brief_gpu_max`
  (default 30 %; a busy GPU is re-checked every tick). Once a day at `brief_digest_time` (local, default `"07:30"`, `"off"` disables;
  skipped if the hub comes up more than 3 h later) a morning digest = all-projects roll-up is queued as an `ollama` job on the brief node
  (`project_id:"*"`), unless a roll-up was already queued since that time. On-demand briefs (`POST /api/projects/{id}/brief`,
  `POST /api/brief/all`) are always allowed. Briefs keep the newest 20 per project. Settings are shown in `GET /api/scheduler` -> `briefs`.
- Hub loop (leader, every 30 min, after leader grace): projects with sessions/commits/jobs newer than their last brief attempt get an `ollama` job (max 6/loop, skip projects with a
  pending brief job; a failed brief is not retried until new activity). Node = config `brief_node`, else the node with the most `metrics.gpu[].mem_total_mb` that has tool `ollama`, agent >= 2.2.0 and
  (if `info.capabilities` is a list/map) the `briefs` capability; online nodes preferred; no capable node -> loop skipped; never falls back to Claude.
- `POST /api/projects/{id}/brief` -> `{id, existing}` (Claude haiku on an auto node, `source:"brief"`); `POST /api/brief/all` -> `{id, projects}` (roll-up, `project_id:"*"`);
  `GET /api/brief/all` -> `{brief: {text,ts,model,job_id}|null, text, ts, model, job_id}` (nested and flat; flat fields are null when there is none).
  Results are stored on job `done` into `briefs`. Brief jobs are hidden from `/api/state`, node detail and `GET /api/jobs` unless `?include_brief=1`
  (accepted by both `GET /api/state` and `GET /api/jobs`).
- Config (config.json): `brief_model`, `brief_node` (`"auto"`/absent = auto), `engine_preference` (default `["claude","codex","ollama"]`),
  `brief_window`, `brief_digest_time`, `brief_gpu_max`.

## G. Scheduler
- `engine: "any"` and `node_id: "auto"`; the hub rewrites `engine` (and `node_id`) before dispatch, so agents never see `any`; job rows keep `req_engine:"any"`, `requested:"auto"`.
- Score `100 - cpu*0.5 - mem_pct*0.3 - active_jobs*15 - (leader?10:0) + (gpu&&ollama?40:0) - (work_root_free_gb<20?50:0)`; ties: free capacity, priority, id.
  Explicit engine on a fixed node is not capability-checked (as in 2.1); `any`/`auto` require the tool (`ollama` also requires agent >= 2.2.0).
- Cooldowns (2.2.1): ONLY a claude/codex job (not `source:"brief"`) that ends (`done`/`failed`) with a NON-ZERO `exit_code`, and only a CLI-style
  limit message in the LAST 20 non-empty lines of its output (`usage limit reached|hit|exceeded`, `limit reached|<epoch>`, `5-hour limit reached`,
  `hit/reached your ... limit`, `rate limit reached|exceeded|hit`, `429 ... rate limit`, `exceeded your current quota`, `quota exceeded|exhausted`).
  Streamed output is never checked; output that merely mentions "rate limit" or "quota" never triggers. Sets `cooldowns[engine]` (reset time parsed
  from `try again in 2 hours 15 minutes`, `try again at 3:45 PM`, `limit reached|<epoch>`; clamp 1 min..12 h; default +30 min) and a `warn` event.
  Held jobs stay `queued` with `wait_reason` (`"claude cooling down until HH:MM"`, hub-local time); `any` jobs pick the next engine, also after they
  were already resolved (`req_engine:"any"`) but not yet dispatched (a job requested `auto` is then re-placed on any node).
- Job `kind` (2.2.1, `POST /api/jobs`): `"code"` (default) | `"text"` (400 otherwise); brief jobs are `text`. Engine `any` resolves to ollama ONLY for
  `kind:"text"`; a code job waits (`wait_reason`) instead of falling to ollama.
- `GET /api/scheduler` -> `{cooldowns:{engine:{until,reason}}, queue_depth, placement_preview:{claude|codex|ollama|shell:[{node_id,score}],
  any:{engine,node_id}|null (code jobs), any_text:{engine,node_id}|null}, engine_preference, briefs:{brief_window, in_window, brief_digest_time,
  brief_gpu_max, brief_node, brief_node_gpu_util, brief_model, interval_s, last_loop}}`; `DELETE /api/scheduler/cooldowns/{engine}` -> `{ok, cleared}`.
- Version gating: `ollama` and resume jobs are only dispatched to agents whose `info.agent_version` (or report body `agent_version`, which also refreshes the stored info) is >= 2.2.0;
  otherwise they stay queued with a `wait_reason`. 2.1.x agents are unaffected.
- Requeue on node loss (user lane, presence path only): a job lost because its node went silent (> 90 s) is requeued ONCE (`attempts` 0 -> 1, status `queued`, node `auto` if it was
  requested auto, engine `any` restored) only if it had < 1 KB output and the node was alive for < 60 s after `started`; otherwise `failed` (`[hub] node offline; job lost`).
  An agent restart (`boot`) still fails its jobs, as in 2.1. System-lane jobs are never requeued.
- `POST /api/jobs` response gains `engine`, `wait_reason`; job rows gain `resume, project_id, attempts, wait_reason, model, req_engine`. `GET /api/jobs?include_brief=&limit=` lists jobs.
- Replication fix (affects all tables): a hub that steps down from leader now does a full authoritative resync from the new leader so its own un-merged writes cannot keep newer `updated` stamps.

# 2.2.1 (hub): fencing, races, partition safety, retention

## Job ownership (stale holders)
- Dispatch items carry `attempt` (the job's `attempts`). The hub records `dispatched_to` on each dispatch.
- `POST /api/agent/jobs/{id}/update` accepts optional `node_id` and `attempt` (2.2.1+ agents SHOULD send both). It is rejected with
  **409 `{"detail":"job reassigned","status":...}`** when the job is not `starting`/`running` (queued again, finished, failed by the hub),
  when `node_id` differs from the current holder, or when `attempt` differs from the current `attempts`. The rejected node then gets the
  job id in `cancel` of its next reports (kill your copy; treat 409 as final for that job). Without `node_id`/`attempt` (older agents)
  only the status check applies.
- A job requeued after its node went silent remembers that node (`prev_holder`, `requeued_at`, replicated): while the job is active
  anywhere else, that node's report `cancel` lists it; it is not handed back to that same node for 60 s (time for the cancel to land).
- Report bodies may carry `agent_time` (epoch seconds or ISO-8601). The hub stores `metrics.clock_skew_s = agent_time - hub now` and
  `/api/health` raises alert kind **`clock_skew`** (warn) when `|skew| > 5 s`.

## Scheduling races
Agent reports run concurrently; placement (`place_jobs`), dispatch, lost-job handling, job updates and cancels are serialized by one
scheduler lock, and every state transition is a conditional UPDATE (`... WHERE status='queued' AND node_id=?` etc.), so a job is never
handed out twice or relabelled while running.

## Partition safety / replication
- `updated` stamps never go backwards per row (`max(now, previous + 1 ms)`), so last-write-wins holds across skewed hub clocks.
- On every leader change a standby drops its sync cursor and does a full resync (the cursor was in the old leader's clock).
- A hub that becomes leader merge-pulls (`/cluster/sync?since=-1`, last-write-wins) from EVERY healthy peer; a leader also merge-pulls a
  peer that still claims leadership (every 10 s) and one that stepped down. Rows it takes over are re-stamped to its clock so its standbys
  pull them too. `/cluster/status` adds `stepdown_seq` (bumped when that hub stops leading) and `merged: {peer: seq}`; a demoted hub keeps
  pulling last-write-wins and only does its authoritative (forced) resync once the leader's `merged[self] >= stepdown_seq` (or after 60 s).
- **Contested leader**: a leader that sees a healthy peer naming a BETTER-priority leader (only its own link to that leader is cut, or a
  healed partition before it steps down) keeps serving but hands out no jobs, sends no fencing cancels, answers job updates with
  **503 `leader contested`**, and makes no presence / brief / retention decisions. It still honours `boot` (fails that agent's jobs).
- `cluster.peers[]` in `/api/state` gains `url`: the peer's first non-loopback URL (the one this hub reaches it on when known).

## Retention (leader, every 10 min; deletes replicate as tombstones)
Finished jobs older than 30 days are pruned, always keeping the newest 200 jobs; briefs keep the newest 20 per project; tombstones older
than 7 days are dropped on every hub.

## Redaction
Server-side (`forge_projects.redact`: session titles, commit subjects, transcripts, forge-job transcripts, brief prompts):
tokens `sk-…` (incl. `sk-ant-`), `ghp_/gho_/ghu_/ghs_/ghr_`, `github_pat_`, `glpat-`, `xox[abprs]-`, `AKIA…`, `AIza…`, JWT `eyJ…`;
PEM blocks `-----BEGIN …----- … -----END …-----` (unterminated: to the end of the text); key=value secrets `password|passwd|pwd|
accountkey|sharedaccesskey|client_secret|api_key = value` (connection strings `Password=…;`, `AccountKey=…;`) keep the key and
redact the value. Forge-job transcripts are redacted before being split into 4000-char events.

# 2.3.0 (hub), workstream R: reliability (CONTRACT-phase3.md §5 R)

## R1 health gate
- `GET /healthz` (no auth, answered locally by standbys): `{ok, node_id, role, version, running_version, db_ok, free_gb,
  checks: {db_write, disk}}`. **503** with the same body when the DB write probe (`healthz_probe` upsert) fails or the data
  drive has less than `healthz_min_free_gb` (config, default 1.0) free. The watchdog treats a 503 with a health body as
  "up but unhealthy" and does not restart the hub for it.
- `GET /cluster/status` adds `local_agent: {online (reported within 90 s), agent_version, bundle_version, last_seen,
  draining_to}` for this hub's own node, `db: {quick_check: "ok"|"reseeded", reseed_pending, last_backup}` and
  `disk: {free_gb, ok}`.
- Release healthy (watchdog probation) = healthz ok AND `eligible` AND `local_agent.bundle_version >= release` within
  `release_health_s` (180). These cases are not judged yet and do not count as a strike: the hub is still syncing (< 180 s),
  the agent is restarting (< 180 s), the agent is `draining_to` the release (< `drain_timeout_s` + 180 s), or the disk is low.
  The agent rule applies only when the agent was reporting before the flip.
- `POST /cluster/bad-version` also raises alert `rolled_back` (key `rolled_back:<node>:<ver>`) and calls
  `ctx.notify("rolled_back", ...)`.

## R3 database safety
- At start, `PRAGMA quick_check` runs before the store opens. If it is not ok, `forge.db(-wal,-shm)` is renamed to
  `forge.db.corrupt-<stamp>`. With peers configured the hub starts empty and stays `eligible=false` (no solo self-election)
  until one full sync from a leader succeeds. Alert `db_reseeded`: error while waiting, warn for 1 h after. Without peers the
  hub restores the newest backup that passes `quick_check` (internally `"restored"`, reported as `"reseeded"`).
- The settled leader runs a backup once a day after `backup_time` (local, default `02:30`):
  `VACUUM INTO <db dir>\backup\forge-YYYYMMDD.db` on a second connection, so writers are not blocked. It keeps `backup_keep`
  (7) files. The db dir becomes `data\private` once S moves the database there.
- `GET /api/backups` (UI) -> `{backups: [{file, size, ts}], last_backup, dir}` (newest first).

## R4 data model
- Job output is stored as append-only `job_output` rows `<job_id>:<seq 8 digits>` (<= 64 000 chars; larger appends are
  split). When the kept text passes 256 000 chars, the oldest chunks are deleted and `jobs.output_min_seq` moves up. Standbys
  delete the same chunks after each sync page, and drop a job's chunks when they apply its `jobs` tombstone (retention uses
  `Store.delete_job_cascade`). `jobs.output` is no longer written except at insert. Readers use the chunks when any exist,
  else `jobs.output` (a job that a 2.2 leader wrote). The first append to such a job copies the legacy text into chunk 1.
- `GET /api/jobs/{id}` keeps `output` (concatenated, with a `[...truncated...]\n` prefix once trimmed) and adds `output_seq`;
  list rows keep `tail`. `GET /api/jobs/{id}/output?since_seq=N` (UI) -> `{chunks: [{seq, ts, text}] (seq > N), next_seq,
  status, truncated}`. `truncated` means chunks after N were already trimmed. A 2.2-written job answers as one chunk, seq 1.
- Presence: every agent report writes the local, unreplicated `presence` row. That includes the system lane
  (`sys_last_seen`, `sys_capacity`, `sys_version`). The replicated `nodes` row is rewritten only when its `last_seen` is
  >= 60 s old (and on an online/offline change by the presence check). The view `nodes_live` lays presence over `nodes`;
  `/api/state`, `/api/nodes/{id}`, `/api/health`, the scheduler, the lease and the presence check read it.

## R5 upgrades
- The user-lane report response carries `drain_timeout_s` (config, default 1800).

## R6 machines lifecycle
- Every hub (real servers only) checks its URL set every 60 s: MagicDNS name and Tailscale IPv4 from
  `tailscale status --json`, plus LAN IPv4s. If tailscale is installed but does not answer, the round is skipped. When the
  set changed, or every `announce_every_s` (300), the hub sends `POST /cluster/join {id, urls}` to the leader. The leader
  replaces the peer's urls and writes nothing when they are unchanged.
- `POST /api/machines/{id}/retire` (UI + step-up) `{confirm: true, uninstall: true, rotate_tokens: false}` -> 202
  `{ok, state: "draining"}`. 400 `confirmation required`; 404 unknown machine; 409 if the machine is already being removed,
  is the only hub, is the hub answering the request and `uninstall` is false, or `uninstall` is requested while
  `forge_uninstall` is not in the catalog.
- `GET /api/machines/{id}/retire` -> `{node_id, state, started, finished, job_id, error}`. `DELETE` cancels while the state
  is `draining` (or after `failed`): drain is turned off and the row is removed.
- Flow (settled leader tick):
  1. `settings.drain=1`: no dispatch and no auto placement. Queued auto jobs go back to the pool; pinned ones are cancelled.
  2. Running jobs finish. After `drain_timeout_s` they get `cancel_requested`.
  3. With `uninstall`: the system job `forge_uninstall {keep_data: false}` runs (`source: "retire"`, the only job a
     draining node gets). The flow waits until the job is done or the node has been silent for 5 min.
  4. The `nodes`, `settings`, `peers`, `sessions` and `repos` rows are deleted (tombstones), along with the local
     presence/metrics/logs. Leftover jobs are failed.
  5. With `rotate_tokens`: `forge_security.rotate(ctx, ["agent","cluster"])`. Then the state is `done`.
  A failed uninstall job (with the node still online), or 30 min without a result, sets `failed` and raises alert
  `retire_failed`.

## Auth (S4)
- UI: cookie `forge_sid` (random 32-byte secret; DB keeps sha256). Legacy `forge_token` cookie / `Authorization: Bearer
  <ui_token>` still work (hash compare); a legacy cookie from a browser (`Mozilla/` user agent) is upgraded to a session,
  reusing the same session per (ip, user agent) for 10 min and minting at most 20 per hour.
- Rate limits key on the client address. `X-Forwarded-For` counts only on a hop that carries `X-Forge-Via` plus

## Enrollment (S3)
- `POST /api/enroll {kind: machine|device, label?}` -> `{id, code: "XXXX-XXXX", kind, expires, hub, command|url}`; `GET
  /api/enroll` = legacy machine form. `GET|DELETE /api/enroll/{id}` (state pending|redeemed|joined|expired).
- Codes: 8 Crockford base32 chars, case/dash-insensitive (I/L->1, O->0), stored as `sha256(normalized)`; TTL `enroll_ttl_s`.
- `GET /agent/install.ps1?code=` checks (does not consume) and substitutes `__HUB__`, `__CODE__` (`__TOKEN__` -> empty).

- `GET /cluster/bootstrap?code=<code>[&node=<id>]` redeems once on the leader (standbys forward) ->

- First run (F): `data\private\firstrun-claim.json {code_sha256, expires, label}` is imported by the leader as a device
  code and deleted; `code_sha256` = sha256 hex of the normalized code.

## Rotation (S5)
- `POST /api/tokens/rotate {which?, confirm: true, force?}` (UI + PIN) -> `{ok, rotated, grace_until}`; 409 lists agents
  (reported in the last 10 min with agent < 2.3) / hubs (< 2.3) that would be locked out. `GET /api/tokens`.
- Old value accepted until `rotated + token_grace_s` (600). During the grace every report response (both lanes) carries
  `rotate: {agent_token, grace_until}`. `forge_security.rotate(ctx, which)` is the R6 entry point.
- Offline nodes that miss the whole grace window must be re-enrolled (their stored tokens are stale).

## Signed bundles (S6)
- `bundle.sig` (zip root) = `{v, version, manifest_sha256, sig, key_id}`; RSA-3072 PKCS#1 v1.5 SHA-256 over the manifest
  (`<sha256> <path>\n`, ordinal sort; skipped: root `bundle.sig|zip|sha256`, `venv/`, `__pycache__/`, `*.pyc`).
- With `signing_pubkey` pinned, `POST /cluster/publish` answers 400 `bundle not signed` / `bundle signature invalid` /
  `bundle contains unsigned code: <path>` (any `__pycache__`, `*.pyc`, `*.pyo` or top-level `venv/` in a fresh
  extraction: the manifest skips them, so they would run unverified), 500 `signing key invalid` for a corrupt pinned
  key (alert `bundle_unsigned`). The hub's re-zip of the running release includes `bundle.sig`. `/cluster/status.signing`.
- `GET /api/security/signing-key` · `PUT /api/security/signing-key {pubkey_xml, replace?}` (UI + PIN; >= 3072 bits; 409
  on a different pinned key without `replace`).

## Step-up (S7)
- `GET /api/stepup` · `POST /api/stepup {pin}` (10 min per session; wrong PINs per 10 min: 5 per session (all
  legacy-token callers are one principal), 10 per IP, 20 per hub -> 429) · `PUT /api/stepup/pin
  {pin, old_pin?}` (needs `old_pin` or a valid step-up once a PIN exists; setting a PIN also steps the session up).
- Protected: admin / destructive `POST /api/jobs`, `POST /api/tokens/rotate`, `PUT /api/security/signing-key`,
  `DELETE /api/peers/{id}` (+ R retire, F maintenance runs). 403 `{"detail": "admin PIN required"|"admin PIN not set",
  "step_up": "required"|"setup"}`. API clients without a session send the PIN per request as `X-Admin-Pin: <6 digits>`.
- Forgotten PIN: `tools\reset-admin-pin.ps1` (elevated, on the leader) writes `data\private\pin-reset.json`; the leader
  clears the replicated PIN and all step-up windows and deletes the file (event `admin PIN cleared ...`).

## Job token (S1) alerts
- Report `metrics.job_token` = `filtered|full|unavailable` (+ `job_token_error`). `/api/health` alerts:
  `job_token_full` (error) for anything but `filtered`, `job_token_unknown` (warn) when missing (pre-2.3 agent),
  `bundle_unsigned` (error) for refused publishes (24 h) and `metrics.watchdog.signature_refused`.

# 2.3.0 (hub) N: alerts and notifications (`hub/forge_alerts.py`, `hub/forge_webpush.py`)

## N1 alert engine (settled leader, every 3 s tick)
Conditions = the core checks (`node_offline`, `disk_full`, `version_behind`, `watchdog_stale`, `clock_skew`, `hub_down`,
`fleet_bad_version`) + `ctx.alert_sources` + alerts raised with `ctx.raise_alert`. Each condition has a `key`
`<kind>:<node_id or ->[:<subject>]` (hub `version_behind` uses subject `hub`, `fleet_bad_version` the version). One open
row per key in the replicated `alerts` table. A condition that has been gone for 2 ticks is resolved (`resolved_by: "auto"`).
Raised alerts are not auto-resolved: they stay open until `ctx.resolve_alert(key)` or a user ack. `task_*` alerts close after
24 h, and any other raised alert closes after 7 days. Resolved rows are deleted after 30 days.
Self-healing (`rollout_in_progress`, `service_restarting`, `version_behind` while the update lease is held, `node_offline` of
the lease holder, or `self_healing: true` from a source) never notifies before `alert_selfheal_grace_s` (900).
- `GET /api/alerts?open=1&limit=100&since=<epoch>` (UI): `{alerts: [{id, key, kind, node_id, level, msg, opened, resolved,
  resolved_by, self_healing, last_notified, data, action}]}`, newest first. `open=0` includes resolved rows, and `since` filters
  on the row's `updated`. `action` = `{label, kind, target}` or null. Defaults: `task_failed` gives `retry_job {job_id}`,
  `task_finished` gives `open_job`, `node_offline` gives `wake_machine {node_id}`, any other alert with a node gives `open_machine`.
  `data.notify_state` is `sent` or `suppressed:rule|dedup|no_channel` once the notification decision has been made.
- `POST /api/alerts/{id}/ack` (UI) -> `{ok}` (404 for an unknown id). Sets `resolved_by: "user"`. A condition that is still true
  reopens as a new row 1 h after the ack.
- `GET /api/health`: `alerts[]` keeps the 2.2 entries and gains `key`, `id`, `opened`, `self_healing` and `action`, followed by
  the open raised alerts.

## N2 notifiers
Notifications go out for: a failed user-lane job (source not `brief`/`sync`), a `done` job with `notify=1`, `node_offline`
open longer than `machine_down_notify_s` (600), and `rolled_back` / `upkeep_failed` / `fleet_bad_version`. Each alert row
is decided once. At most one notification goes out per key per 6 h, so a flapping machine does not page twice.
`ctx.notify(kind, ...)` uses the same rules (key `<kind>:<node>[:<job>]`), and kinds outside these rules are dropped.
Sends run on a background worker thread.
Prefs (`prefs` table, replicated, so they follow the leader): `notify.ntfy {enabled, server, topic}`, `notify.webpush {enabled}`,
`notify.rules {task_failed, task_finished, machine_down, autorepair}`, `notify.deadman {enabled, url, send_fail}`, plus
`notify.deadman_state {last_ping, last_ok, last_error}`.
- `GET /api/notify/settings` (UI) -> `{ntfy: {enabled, server, topic, subscribe_url}, webpush: {enabled, vapid_public_key,
  available, devices}, deadman: {enabled, url, send_fail, last_ping, last_ok, last_error}, rules}`. The first GET on the
  leader creates the VAPID P-256 key pair (`secrets` rows `vapid_private_key` / `vapid_public_key`, base64url; the public key
  is the 65-byte uncompressed point).
- `PUT /api/notify/settings` (UI): takes a partial of the same shape and returns the full shape. It answers 400 for a bad
  server or dead-man URL, a topic that does not match `^[A-Za-z0-9_-]{8,64}$`, a non-boolean flag, an unknown rule, or an
  enable without a topic or URL.
- `POST /api/notify/ntfy/topic` (UI) -> `{topic: "hm-<20 base32>", subscribe_url}` (not saved). The UI shows the URL and a QR
  code for it.
- `POST /api/notify/test` (UI) `{channel?: ntfy|webpush|all}` -> `{ok, results: {ntfy?: "ok"|"<error>", webpush?: {sent, failed}}}`.
- `POST /api/push/subscribe` (UI) `{endpoint (https), keys: {p256dh, auth}, label?}` -> `{ok, id = sha256(endpoint)[:32]}`.
  Invalid keys give 400; a hub without `cryptography` gives 503. `DELETE /api/push/subscribe` `{endpoint}` -> `{ok, removed}`.
  A push service answer of 404/410, or 5 failures in a row, deletes the subscription.
- ntfy is published as JSON to `<server>/` (`{topic, title, message, tags, priority: 4 for errors else 3, click}`), with
  `click = <public_url>/#/...`. `public_url` comes from config, else the leader's first `*.ts.net` peer URL, else its first
  non-loopback URL.
- Web Push uses RFC 8291 aes128gcm with VAPID ES256 (`sub` = config `vapid_subject`, default `mailto:hivemind@example.com`),
  `TTL: 86400`, `Urgency: high` for errors, and `Topic` = a hash of the alert key. The payload is
  `{title, body, url: "#/...", tag: <alert key>}`.
- `POST /api/jobs` accepts `notify: bool` (default false). Job rows carry `notify` (0/1).

## N3 dead-man switch
When `notify.deadman.enabled`, the settled leader GETs `url` every `deadman_every_s` (300 s, timeout 10 s). If `send_fail` is
set and any `error` alert is open, it GETs `url + "/fail"` instead. The result is shown under `deadman` in the settings response.

## N4 morning brief
The roll-up prompt (`p2.digest_extras`) ends with the overnight alerts and finished tasks since 18:00 local time the previous
day (redacted). `GET /api/brief/all` (replaced by `forge_alerts`, amendment N-1) keeps its body and adds
`overnight: {alerts: [{kind, node_id, msg, opened, resolved}], finished: [{id, prompt (<= 80), status, node_id, finished}]}`
(at most 30 of each; `task_finished` alerts are left out because they appear under `finished`).
